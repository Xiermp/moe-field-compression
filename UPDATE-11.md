## Что нового

### 1. probe_capacity.py — плечо `postact`
Решающий тест гипотезы H1 (кросс-члены SwiGLU при смешивании координат ДО
нелинейности) на РЕАЛЬНЫХ весах одного блока:

    python probe_capacity.py --root <cache> --block 20 --arm postact --steps 800

Идентичные параметры поля, но композиция «Вариант A» из внешнего ревью:
общий пре-бейс `x@wgud^T`, низкоранговые дельты и НЕЛИНЕЙНОСТЬ по каждому
выбранному эксперту, выход = `sum_e z_e * FFN_e(x)`. При top_k=1 совпадает
с preact точно. Сравнивать с плечом `cont` на том же блоке.

### 2. hf_pipeline.py — «железный тест» `--verify-topk K1,K2,...` (теперь СВИП)
После обычного verify перезапускает base vs artifact с MoE top_k=K на ОБЕИХ
моделях (роутеры патчатся в рантайме), KL считается LIVE (кеш lp построен
под top-2 и непригоден). Стриммер базы собирается ОДИН раз и переиспользуется
для всех K списка:

    python hf_pipeline.py <ваши модельные флаги> --stages verify --verify-topk 1
    python hf_pipeline.py <ваши модельные флаги> --test-only --verify-topk 1,4,8

Авто-вердикт по отношению KL(topK)/KL(опорного k; опора = 2, или N при
--force-topk):
  - < 0.6  — разрыв схлопнулся без смеси -> H1 (композиция) -> постакт-режим;
  - > 0.85 — разрыв остался -> H2 (ёмкость дельт) -> плечо bank2;
  - иначе  — смешанная картина.

### 3. hf_pipeline.py — режим `--field-mode {preact,postact}` (по умолч. preact)
Postact теперь СКВОЗНОЙ: фит (fit_sig включает field_mode — смена режима
честно перефитит), refine-проходы, экспорт артефакта (config.field.field_mode)
и рантайм-шаблон modeling_field.py (читает режим из конфига). Параметры поля
ТЕ ЖЕ самые — инициализация/пул/файлы совместимы между режимами.

    python hf_pipeline.py <флаги> --field-mode postact --stages fit,save,verify

Цена: ~+1 down-GEMM на токен (стоимость остаётся ниже оригинального top-2 MoE).

### 4. hf_pipeline.py — режим `--test-only` (тесты без обработки)
Замокать план на `texts,base,verify`: ppl/KL/демо-генерация по ГОТОВОМУ
артефакту и кэшам, никакого fit/refine/save. Повторный прогон без других
флагов берёт всё из кэша (минуты); с --force-topk база перестримится один
раз под новым k:

    python hf_pipeline.py <флаги модели> --test-only
    python hf_pipeline.py <флаги модели> --test-only --verify-topk 1,4,8

### 5. hf_pipeline.py — `--force-topk N` (сквозное переопределение routing)
Форсирует MoE top_k=N на ВСЁ время запуска: и в базе (стриминг из GGUF), и в
артефакте (поле). Патчатся все модули с int top_k (.top_k у роутеров базы,
.k у field-блоков) + config.num_experts_per_tok. Печатает баннер вида
`FORCE-TOPK [base] -> k=N (config had M); routing modules patched: P` —
значение M это родной k из метаданных/артефакта (заодно контроль, что вся
цепочка жила на ожидаемом k). Если P=0 — громкое WARNING (переопределение
не дотянулось до форварда).

Кэш под форсированным k ИЗОЛИРОВАН: lp_base_topkN + eval_tokens_topkN.pt —
родные кэши и стандартные цифры verify не трогаются. Совместим с
--test-only и --verify-topk (в свипе K == N пропускается как дубликат).

    python hf_pipeline.py <флаги модели> --test-only --force-topk 8

Итог импирики 2026-09-07: k=8 даёт лучшие метрики, чем родной k=2 —
ошибки поля «врозь» и усредняются смесью; дополнительный аргумент к H2
(представление дельт), а не к роутеру. k у field-модели — свободный
рантайм-крутилка: веса не меняются, качеством можно управлять на инференсе.

## 11.2 (2026-09-07): IRON PROBES - декомпозиция остаточной KL по четырём дефектам

IRON TEST (11/11.1) развёл H1/H2, но три дефекта остаются неразличимыми внутри
общей KL: слепота на старте, кросс-шум SwiGLU preact, дезориентация без
промпта. 11.2 добавляет три пробы - A и C почти бесплатны, B стоит +2 живых
прохода и только при явном флаге. Всё остальное (кэш пула, lp, фиты, вердикты)
не тронуто и НЕ требует перепрогонов.

### Проба A - "слепота на старте" (бесплатно, в каждом прогоне)
Каждое eval-окно - холодный старт (сырой текст без промпта), поэтому KL теперь
копится ПО БАКЕТАМ ПОЗИЦИЙ 0-7 / 8-31 / 32-127 / 128+ и печатается строкой
"KL by position" в ТРЁХ местах: у reference (eval_vs_cache_disk) и в каждом
проходе IRON TEST. Первый бакет в разы выше остальных -> дефект реально сидит
на старте окна; его доля = цена починки. Логика бакетов юнит-тестом покрыта
(взвешенное среднее == общей KL; выравнивание строк точное).

### Проба B - "дезориентация без промпта" (--iron-prompt, +2 прохода)
    python hf_pipeline.py ... --test-only --iron-prompt "Ты - полезный ассистент."
На референсном k артефакт и база прогоняются дважды: без промпта и с промптом,
ПРЕПЕНДИРУЕМЫМ к каждому окну как чистый контекст - ОЦЕНИВАЕМЫЕ ЦЕЛИ ТЕ ЖЕ
САМЫЕ (срез [m:] выравнивает строки логитов), так что KL напрямую сравнимы.
- KL падает на ~10%+ -> "дезориентация" подтверждена (дефект обвязки: фит
  видел сырые чанки; артефакт в чате живёт в другом распределении);
- KL растёт -> артефакт переобучен на безпромптное распределение;
- <= ~10% -> гипотеза не подтверждена.
Промпт токенизируется с add_special_tokens=True; оба прохода переиспользуют
одну загрузку base (стриминг GGUF деквант запускается один раз), sweep k
после этого переиспользует её же.

### Проба C - "кросс-шум SwiGLU preact" (offline, НОЛЬ прогонов модели)
Новый скрипт: probe_preact.py. Артефакт грузится как обычная HF-модель,
для входов x из СОХРАНЁННОГО пула пар каждый MoE-блок считается в ОБОИХ
режимах композиции (переключение field_mode, параметры идентичны):
    rel_pre  = RMS(y_preact - y_base)/RMS(y_base)
    rel_post = RMS(y_postact - y_base)/RMS(y_base)
    comp_gap = RMS(y_preact - y_postact)/RMS(y_base)  <- чистый кросс-шум
    python probe_preact.py --src field_TAG_r128 --pool cache_TAG [--topk 8] [--blocks 0,1,2]
comp_gap >= ~50% rel_pre -> композиция доминирует (починка: --field-mode
postact / рефит); comp_gap мал при больших rel_* -> это ёмкость ранга (H2,
банк/ранг). --topk показывает зависимость кросс-членов от ширины смеси.
Ни base, ни GGUF не нужны; работает на CPU.

### Как читать связку
Проба A даёт вертикальный разрез (где в окне), C - структурный (что в блоке),
B - контекстный (обвязка). Порядок: A+C сразу (C вообще офлайн), B - одним
запуском с --iron-prompt и --verify-topk вместе (промпт-пара идёт ПЕРЕД
sweep и переиспользует загрузку базы, так что лишних деквантов нет).
