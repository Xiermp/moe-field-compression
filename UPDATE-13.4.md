## 2. Парадокс, который остался

На КАЖДОМ из 23 блоков: `init baseline (eval8)` ~= `pure-centroid` в пределах
+-2% (например blk0: 0.00426 vs 0.00424; blk20: 0.66945 vs 0.68311).

Но banner говорит: whitened capture **gu 99.1% / dn 72.3%**. Если бы инит
функционально работал, step-0 mse должен был бы сесть на ~(1-capture) x
pure-centroid (~0.3x), а не на ~1.0x. Два факта несовместимы - значит, одна
из линз врёт, или ценность инита съедается между банком и mse.

Важно: **банк этого прогона старый** (построен до 13.3): в banner-строке НЕТ
суффикса «| честный (Frobenius)» - `caps_raw` в npz отсутствуют. Т.е. 99.1/72.3
- это ТОЛЬКО отбеленная линза, честных чисел в этом прогоне не было вообще.
Флаги демпфера (`--wh-damp-frac`) тоже не применялись (bank уже был на диске,
`ensure_t2_init` его переиспользовал).

Кандидаты (взаимоисключающие), от наиболее к наименее вероятным:

| # | Гипотеза | Механизм | Чем проверяется |
|---|----------|----------|-----------------|
| A | **Кросс-члены preact** | Фит-модуль по умолчанию `--field-mode preact`: один silu на СМЕШАННЫХ пре-активациях против per-expert silu базы. Даже ИДЕАЛЬНЫЕ дельты оставляют ошибку композиции порядка ошибки центроида. | ARM POSTACT: те же параметры в postact |
| B | **Mean-of-ratios врёт** | capture в банке - среднее ПО ЭКСПЕРТАМ, mse в пуле - по ТОКЕНАМ. При дисбалансе роутера (бывает 0..cap токенов/эксперт) горячие эксперты с низкой капой съедают всё. | LOAD x CAP: капа топ-квартиля загрузки vs средняя |
| C | **Вырожденность ковариации (dn)** | Отбеленная капа завышена: захват живёт в выбросах Σ, честная доля массы дельты ниже. | RAW CAP per expert (или пересборка банка 13.3) |
| D | **Хендофф банка -> модуль** | init_svd_blk несёт не то, что построил банк (тихая порча при сохранении/загрузке). | HANDOFF: npz vs init_svd бит-в-бит |
| E | **Недосходимость фита** | 300 шагов полировки не добирают то, что в принципе достижимо на замороженном базисе. | ARM LONGFIT (продолжение поливки) |

## 3. init_audit.py - раскладка на месте

Все армы считаются на ТЕХ ЖЕ парах пула, что ел stage-5 (модель не нужна),
полно-пульным mse (та же метрика, что step-0/финал в логе, но детерминированная):

```
INIT          модуль как в stage-5           -> ~ step-0 mse из лога (санити харнесса)
CENTROID      ядра = 0                       -> ~ pure-centroid из лога
FIT           параметры из fit_blk           -> ~ финальный mse из лога
POSTACT       INIT-параметры, postact        -> цена композиции (кросс-члены SwiGLU)
POSTACT-FIT   FIT-параметры в postact
LONGFIT       (--longfit-steps N) продолжение полировки из INIT,
              adamw/train=cores/_lr-warmup20 -> тест недосходимости
HANDOFF       npz t2_k{rank} vs init_svd бит-в-бит (всегда)
LOAD x CAP    загрузка экспертов vs per-expert whitened caps (всегда, из npz)
RAW CAP       per-expert честная капа из дельт модели (опция, --gguf/--src/--local-path)
```

Запуск (2-3 блока хватит; один блок - секунды, RAW CAP добавляет стриминг
экспертов блока):

```bat
python init_audit.py --pool results\cache_..._r64 --fit-dir results\field_..._r64 ^
    --blocks 0,10,20 --rank 64

:: с честной капой по экспертам (как в verify, но по всем экспертам блока):
python init_audit.py --pool ... --fit-dir ... --blocks 0,20 --rank 64 ^
    --gguf <файл.Q4_K_M.gguf> --src <HF-каталог модели>

:: с тестом недосходимости (блок 0, ~пара минут):
python init_audit.py --pool ... --fit-dir ... --blocks 0 --rank 64 --longfit-steps 2000
```

Чтение: `INIT/CENTROID` сравнивай со строками `step 0`/`pure-centroid` из лога
stage-5, `FIT` - с финальным mse блока (числа должны совпасть в пределах
eval-шума - это санити харнесса). Вердикты печатаются в конце, по приоритету:

| Вердикт | Действие |
|---------|----------|
| POSTACT(init) на 25%+ ниже INIT | кросс-члены - главный потолок -> перезапуск пайплайна с `--field-mode postact` (+1 GEMM; фит/refine/экспорт его знают с 10.9) |
| LONGFIT << FIT (90%+) | фит недосходится -> поднять `--fit-steps` (полировка ещё не в полу) |
| капа горячих экспертов << средней | mean-of-ratios подтверждён -> таргетировать ранг/фит на горячих (или выровнять пул по загрузке) |
| RAW dn << whitened dn (70%+) | вырожденность ковариации -> пересобрать банк с `--force --wh-damp-frac 0.01 --wh-damp-base mean-diag` |
| HANDOFF MISMATCH | курок: присылай вывод - чиню хендофф |
| INIT ~ CENTROID, а FIT << CENTROID, но RAW/капы высокие | смотри LOAD x CAP; если и там чисто - ранг (см. ниже кривую capture-vs-k) |

## 4. Кривая capture-vs-k бесплатно (префикс-трюк)

`build_block_t2` строит общий базис K = max(--k) и получает ВСЕ меньшие k
префиксами столбцов U/V - т.е. **одна** пересборка даёт капу для всей лестницы:

```
python whbank_build.py --pool results\cache_..._r64 --src <HF-каталог> ^
    --gguf <файл.gguf> --k 32,64,96,128 --variants t2 --force
```

Это одновременно: (а) честные `caps_raw` в npz (13.3) - на следующем stage-5
banner напечатает обе линзы; (б) кривая «dn capture vs k» - если dn при 96/128
выходит на плато, ранг не лечит (плоский спектр -> спайки UPDATE-14 или
composition), если растёт - ранговый бюджет перекидываем с gu (99.1% при 64 -
запас) на dn. Отчёт build печатает капу по всем вариантам; `--report-only`
затем покажет свод без пересчёта.

## 5. Про --src (ответ на вопрос)

У `whbank_build.py`/`init_audit.py` три способа указать источник весов - они
те же, что в hf_pipeline:

- `--src` - **HF-каталог или light-catalog** (имя на HuggingFace или локальный
  каталог с config.json): из него читается КОНФИГ/скелет модели;
- `--gguf` - путь к GGUF-файлу: из него читаются ВЕСА (стриминг);
- `--local-path` - полный HF-лоад распакованной модели (только для мелких).

Для твоего прогона (GGUF): указывай **и то и то** - `--src` тот же, что ты
давал в hf_pipeline, `--gguf` - тот же файл Q4. «Слой прочитать не может»
означал, что --src не был дан вовсе (без него стриминг-раннер не знает
геометрию). В init_audit та же семантика + гвард: `--gguf` без `--src` -
внятная ошибка.
